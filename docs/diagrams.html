Explainable Satellite Anomaly Detection — System Diagrams

Four diagrams covering the system: how components connect, how a single telemetry reading moves through detection to an operator alert, how the underlying data is modeled, and who uses the system for what.

01

System Architecture

Two data sources feed one pipeline: a live telemetry stream for the demo, and labeled historical missions for training. The model and explainability engine sit in the middle; the alert manager is the only component that writes to storage and pushes to the operator.

02

Runtime Workflow

What happens to one telemetry reading, in order. Most readings exit early at the threshold check — only the ones that actually deviate pay the cost of correlation and explanation.

03

Database Schema

Seven tables. The design keeps AnomalyContribution as its own table rather than a column on Anomaly, because one anomaly can implicate several channels at once — that's the row-level data the explainability engine needs to point to.

04

Use Case Diagram

Three human roles plus one external system. The dashed ellipse (Detect Anomaly) isn't triggered directly by anyone — it's pulled in automatically whenever the operator's monitoring session runs.
